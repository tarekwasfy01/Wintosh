# Darling external-component provenance review

This file records the result of a source-tree inventory and is not a relicensing
statement. The original license and notice files shipped by each component
remain authoritative.

Inventory root: `darling-source/src/external`

At the current checkout the root contains 150 component directories. A
recursive filename scan found recognizable `LICENSE`, `LICENCE`, `COPYING`, or
`NOTICE` files in 2 components and none in 148 components. The 148 results are
therefore `review-required`, not proof that the code is unlicensed: many
upstream projects keep notices in source headers, nested vendored trees,
package metadata, or repository-level files.

The follow-up provenance check found `.git` markers in 149 of the 150
component directories, but the current checkout cannot resolve those markers
to valid `HEAD` commits or worktrees. One component,
`libpthread_workqueue-0.8.2`, has no component-local `.git` marker. A marker
is not treated as usable provenance unless Git can verify `HEAD`; even valid
Git metadata would not replace a license audit or a pinned commit/tag record.

Before redistribution, each review-required component must be resolved against
its upstream repository/tag and its applicable license/notice text must be
copied into the distribution's corresponding-source bundle. Until that audit
is complete, generated Windows objects and binaries must not be described as a
license-clean Darling release.

The main source inventory remains
[`SOURCE-LICENSE-INVENTORY.csv`](SOURCE-LICENSE-INVENTORY.csv); this document
adds the per-component gap count and preserves the conservative provenance
boundary.

The reproducible per-component output records every recursively detected
license/notice filename for a component (semicolon-separated), rather than
silently keeping only the first match. The output is
[`EXTERNAL-COMPONENT-PROVENANCE.csv`](EXTERNAL-COMPONENT-PROVENANCE.csv),
generated by
[`generate-external-provenance.ps1`](generate-external-provenance.ps1). The
current generated result contains 150 rows, no valid Git checkout metadata,
149 invalid `.git` markers, one component without a marker, and 149 recovered
upstream URLs from the authoritative Darling `.gitmodules` mapping. These
URLs are origin-only
evidence; they do not prove a commit, tag, or exact source version. There are
2 recognizable
license-bearing component trees, one manually recorded header-evidence case,
and 147 remaining license review cases.

Manual follow-up for `libpthread_workqueue-0.8.2` found BSD-style
redistribution terms in `include/pthread_workqueue.h`, `src/api.c`, and
`src/private.h`, plus Apache-2.0 notices in selected test sources. Because
these are header-level notices and the checkout has no Git metadata, the
component remains a manual review case until its exact upstream release and
complete notice set are pinned.

Reproducibility check: 150 CSV rows, Git metadata counts
`invalid-marker=149`, `absent=1`, and no valid `present` rows; license status
counts remain `present=2`, `header-evidence=1`, `review-required=147`.

The first manual pass should prioritize the 22 files with multiple license
markers, especially candidates containing GPL/LGPL/MPL together with permissive
