## Execution boundary

The supported architecture target is the native Windows adapter and runner;
WSL is optional reference/backend infrastructure, not a runtime prerequisite.
On the current host, direct WSL probing returns `Wsl/E_ACCESSDENIED`, so no
WSL-backed Darling execution is claimed or required for the native smoke-test
suite.

The native `wintosh.exe` Release target was built and verified with
`--help`, `--version` (`Wintosh 0.1.1`), and `--diagnose-host`. The host
diagnostic confirms the current x86_64 native target and the fail-closed
boundaries for i386/ARM64 on this host. A repository-owned synthetic x86_64
Mach-O fixture is now bundled, so `--inspect` and native execution are proven
for that controlled fixture; arbitrary macOS binaries remain unclaimed.

The runner also provides `--init-prefix <directory>`, which creates the
documented Darwin directory layout (`System/Library/Frameworks`, `usr/lib`,
and the relevant `Library` data roots) without downloading or fabricating
Apple libraries. See [MACOS-DIRECTORY-MAP.md](MACOS-DIRECTORY-MAP.md). The
repository-owned x86_64 fixture now proves `--inspect` and
native execution; real system dylibs and frameworks are still not bundled.

The runtime-provider fixture now verifies a three-image provider chain:
`RuntimeClient.macho` resolves and calls `_libSystemInit` from the repository's
own `libSystem.B.dylib`, which itself depends on the repository's own
`libsystem_platform.dylib`. This proves the native provider graph and call
path, but these files are test providers rather than Apple's system libraries.

The current native CTest inventory contains 59 tests.  The `tlv_smoke`,
`thread_smoke`, `pthread_sync_smoke`, `host_api_smoke`, and
`darwin_windows_broker_smoke` families cover the Windows-backed TLS,
pthread-lifecycle, synchronization, and Mach process boundaries.  A
repository-owned Mach-O provider containing the real section families
`__thread_data`, `__thread_bss`, `__thread_vars`, and `__thread_ptrs` now
exists at `wintosh-windows/fixtures/x86_64/tlv-provider`.  It is generated by
the `--emit-tlv` smoke utility and exercises section mapping and
initialization; it remains synthetic and is not a redistributable Apple
`libpthread` binary.

The complete current Clang CTest run passes 59/59 tests.  This includes the
Mach-O/dyld, Objective-C/CoreFoundation, errno/signal, Mach IPC, process,
filesystem, socket, terminal, and Windows host-boundary families.  This is a
repository-wide regression result for the current Wintosh implementation, not
a claim of full Darling or macOS compatibility.

The runner smoke now executes a controlled `.app` bundle as well as inspecting
it: the bundle path resolves to `Contents/MacOS/<bundle-name>`, its Mach-O
entry receives the expected single argument, and the process returns exit code
1.  This is a repository-owned bundle fixture; it does not prove arbitrary
real-world application bundles or their Apple frameworks are runnable.

The bundle resolver now honors a simple XML `Info.plist` value for
`CFBundleExecutable` and falls back to the bundle directory name when the key
is absent or malformed.  The runner smoke uses a deliberately different
bundle name and executable name to verify this path.  The fixture also
includes surrounding whitespace and an attribute on the `<string>` tag,
covering these common plist formatting variants without claiming to be a
complete property-list parser.

The runner also reads the common `bplist00` binary format for the
`CFBundleExecutable` string (ASCII and basic UTF-16 strings) and retains the
directory-name fallback for unsupported or malformed plists.  The runner
smoke covers both the formatted XML path and a binary-plist bundle path; this
is intentionally a focused key reader, not a general Foundation plist API.
Binary dictionaries with an extended object count are accepted as well, while
the implementation deliberately remains bounded to the executable lookup.
Malformed binary-plist count metadata is rejected safely and uses the normal
bundle-name fallback rather than being treated as executable metadata.
The runner smoke now executes that malformed-plist fallback path end-to-end.

`MachOImage::HasCodeSignature()` and `wintosh --inspect` now expose whether an
`LC_CODE_SIGNATURE` load command is present.  This is metadata detection only:
Wintosh still does not validate the embedded Apple CodeDirectory or CMS
signature and never treats presence as authenticity.
`CodeSignatureRange()` additionally exposes the validated payload offset and
size for a future verifier, covered by the Mach-O UUID/signature smoke test.

The supplied ABI-bridge PoC was independently re-run on this Windows x64
host with LLVM 23.1.2: Clang compiled and linked it with the MSVC target, and
the native executable reported `RESULT: PASS` with exit code 0.  Its measured
checks cover eight integer arguments, mixed integer/floating-point arguments,
the hand-written variadic save-area path, host-to-guest callee-saved registers,
and System-V entry stack alignment.  This validates the toolchain and calling
convention PoC only; the bridge is not yet connected to Wintosh's Mach-O
loader or host-export table.

The first loader integration is now present: `ExecuteEntryNoArgs`,
`ExecuteInitializers`, `ExecuteTerminators`, and the compatible `main` entry
are expressed through the Wintosh-owned `abi::GuestFn` aliases.  The 58-test
Release run was built with MSVC; on that compiler `GuestFn` is deliberately a
normal function pointer and is never used for a real guest entry.  The real
`CompatibleMain` path now fails closed with
`real Mach-O execution requires a Clang build with System-V ABI support`.
Existing repository fixtures must opt into `SyntheticCompatibleMain` (the CLI
spelling is `--startup-abi synthetic-main`).  This keeps their Windows-ABI
smoke coverage explicit without presenting it as Apple ABI execution.

The bridge now also provides fixed-arity `_puts` and `_exit` export entry
points through `darling_windows_host_symbol`.  After reconfiguring CMake to
pick up the new source file, `wintosh_host_api_smoke` and `wintosh_dyld_smoke`
both pass.  These exports are ready for Clang/System-V guest calls; the
default MSVC build still uses the compatibility ABI fallback, so this is not
yet evidence that a real Mach-O import call has executed.
The bridge translation unit and complete native runner now compile and link
with clang-cl/lld-link and LLVM's integrated assembler on Windows. The Clang
configuration is kept separate from the MSVC build; the latter remains the
supported synthetic-fixture and broad regression configuration.
The new `abi_bridge_smoke` additionally calls `_puts` directly and verifies
that the Mach-O `_puts` lookup returns the same address; this is a fixed-arity
host-export smoke only, not yet the Clang System-V guest-call gate.

The loader now recognizes `dyld_stub_binder` as a guarded host export.  This
allows a chained-fixups image that carries legacy stub metadata but does not
execute lazy binding to continue through binding preparation; if the binder is
actually invoked, the guarded export terminates with an explicit unsupported
diagnostic instead of silently calling an incompatible function.  Chained
images also skip the legacy indirect-symbol slot walk because their pointer
locations come from the chained starts table.  The supplied chained fixture
now passes the MSVC fail-closed gate (`real Mach-O execution requires a Clang
build with System-V ABI support`); forcing it through `synthetic-main` is
intentionally invalid and terminates before producing guest output.

The dyld resolver now also checks `Contents/Frameworks` and `Contents/PlugIns`
as scoped fallbacks for `@rpath/...` dependencies of a bundle executable when
the image has no explicit `LC_RPATH`.  The dyld smoke fixture proves the
`Contents/Frameworks` case; this is path resolution only and does not imply
that arbitrary Apple frameworks are executable on Windows.

Framework shorthand resolution also covers versioned bundles through
`Name.framework/Versions/Current/Name` and `Versions/A/Name`; the smoke fixture
proves the concrete `Versions/A` layout.

The Objective-C/CoreFoundation tests verify class and selector registration,
typed message-send bridges, blocks, Foundation values, run loops, and
CoreFoundation collections.  They do not provide an Objective-C exception
unwind ABI: no `@throw`/`@catch` personality routine or `objc_exception_*`
compatibility layer is currently shipped.  C++ exceptions must not be treated
as proof of that Darwin behavior.

The Wintosh-owned `objc_exception_smoke` additionally verifies a scoped
callback exception carrier: an Objective-C object can cross the bridge and be
caught by the matching Wintosh adapter, while normal callback return remains
distinct.  This is a project-local transition API, not an Apple-compatible
compiler personality or DWARF/SEH Objective-C unwind implementation.

The focused TLS/pthread regression set was rerun on the current Release build:
`wintosh_tlv_smoke`, `wintosh_thread_smoke`, `wintosh_pthread_sync_smoke`,
`wintosh_host_api_smoke`, `wintosh_dyld_smoke`, and `wintosh_macho_smoke`
all pass (6/6).  This is evidence for the Windows host bridge and loader
paths, not evidence that an arbitrary Apple pthread implementation can already
be loaded.

The adjacent startup/POSIX boundary set also passes 5/5 on Release:
`wintosh_errno_smoke`, `wintosh_signals_smoke`,
`wintosh_startup_trampoline_smoke`, `wintosh_macho_entry32_smoke`, and
`wintosh_runner_smoke`.  This verifies the current Windows-backed errno and
signal bridges, the tested startup trampoline, 32-bit entry dispatch, and
runner argument handling; it does not expand Mach-O TLS thunk support.

The executable `TLVClient.macho` currently proves the safe path: all four
Darwin TLS sections are initialized before its entry returns, and the runner
exits with code 0.  A hand-written Mach-O-side call through the initialized
`DarwinTLVDescriptor::thunk` was also isolated experimentally, but still
causes an access violation at the Mach-O-to-host ABI boundary.  That call is
therefore not shipped as a capability claim; the native `tlv_smoke` test
continues to cover the thunk and per-thread resolution directly.  The next
required step is an ABI trampoline with a verified Windows x64 call frame,
followed by a Mach-O-side value and second-thread isolation assertion.

An independent entry sentinel (`mov eax,42; ret`) returned 42 from the loaded
`TLVClient.macho`, confirming that its `LC_MAIN` address is executed.  A
RIP-relative read of the `__thread_data` template did not return the template
byte; that template is copied into per-thread storage and is not ordinary
global data at the section address.  The remaining ABI work is therefore to
reach the per-thread object through the descriptor thunk from Mach-O code.

## What is included in a source release

Include the Windows port source, all documentation, and the `licenses`
directory. Do not vendor the large upstream reference checkouts; link to the
original repositories and keep every applicable license and notice here. A
source release must not silently replace a third-party license with the
Wintosh-original MIT notice.

## What is not claimed

This manifest proves that the current files are present in this workspace. It
does not prove that all 150 Darling external components are license-cleared,
that the NTFS-incompatible Heimdal checkout is complete, that the global build
passes, or that arbitrary macOS applications run on Windows. Those boundaries
remain in [STATUS.md](STATUS.md) and [RELEASE-CHECKLIST.md](RELEASE-CHECKLIST.md).

## First real Clang/SysV Mach-O run on Windows

The project now has a native Clang-cl Ninja configuration that uses LLVM's
integrated assembler for the Darwin-start trampoline when MASM `ml64` is not
available. The MSVC/MASM path remains unchanged. With LLVM 23.1.2,
`build-windows-clang-native3/wintosh.exe` compiled and linked successfully on
Windows.

The supplied chained-fixups fixture was then executed through that Clang build:

```text
hello from guest
NO_ARG_EXIT=0
hello from guest
ONE_ARG_EXIT=7
```

This is the first end-to-end proof of a real x86_64 SysV Mach-O entry and the
fixed-arity `_puts`/`_exit` bridge on Windows. It covers the chained fixture
only; the Classic fixture, lazy binding, Darwin `crt1` startup, variadic
exports, and arbitrary Apple frameworks remain unimplemented or unverified.

The Classic Mach-O fixture now also executes through the Clang build. Its
`__stubs` section is accounted for when walking the indirect-symbol table;
stub entries are consumed as metadata while only lazy/non-lazy pointer
sections are patched. The verified Classic result is likewise:

```text
hello from guest
CLASSIC_NO_ARG_EXIT=0
hello from guest
CLASSIC_ONE_ARG_EXIT=7
```

This proves the current fixed-arity classic binding path for `_puts` and
`_exit`; it does not yet prove arbitrary lazy-binding protocols or variadic
function calls.

The host symbol table now exposes a named SysV `printf` bridge entry. Under the
Clang build, a dedicated x86_64 register-save trampoline translates the SysV
integer/pointer variadic arguments into a Windows helper call. The direct
`abi_bridge_smoke` gate now verifies `%d`, `%s`, `%u`, `%x`, `%X`, `%c`, `%%`,
and newline handling. Floating point, length modifiers, positional arguments,
and the full `printf` format language remain unsupported. The Clang trampoline
also saves the SysV XMM register area and verifies `%f`/`%g` for `double`.
The bridge now accepts the tested `l`/`ll` integer modifiers and `lf` alias.
The MSVC build remains deliberately fail-closed
and reports `SysV variadic printf bridge is not implemented`; it does not run
real SysV guest code.

The Clang CTest suite now also runs `wintosh_macho_printf_e2e`. It generates a
repository-owned temporary Mach-O which imports `_printf`, calls it through the
loader's lazy-binding path, and verifies the output `mach-o printf 7`. This is the
first verified Mach-O-to-variadic-bridge path; it remains a narrow integer-only
fixture. The same test now places that image in a minimal `Printf.app` bundle,
resolves `Contents/Info.plist` and `Contents/MacOS/Printf`, and executes it
through the bundle path. This validates bundle entry resolution, not system
framework compatibility. The legacy `dyld_stub_binder` callback itself remains
fail-closed; Wintosh currently pre-applies parsed lazy-bind actions before
entering the image.

## Latest verified native adapter families

The current local branch additionally contains a prefix-relative Preferences
adapter. Its tested subset includes application and suite plist domains,
registration and argument values, managed/effective read-only views,
cross-process named-event wakeups, FIFO key events in a `.events` sidecar,
orphaned `.tmp` plist recovery, and reentrant observer snapshots including
observer self-removal and observer addition during delivery. The pthread
synchronization smoke also verifies priority-ceiling attribute propagation and
old-value return behavior. These are Wintosh-original Windows adapters with
their provenance recorded in `PRIMITIVE-MATRIX.csv`; they do not claim the
complete Foundation, notification-center, scheduler, or Objective-C ABI.

Preferences observer delivery now also defers store destruction requested from
inside an observer until the callback snapshot and the active mutation lock
are finished. The callback-destruction smoke covers this lifetime boundary;
the full NSUserDefaults ABI and cross-process observer lifecycle remain open.

External preference reloads now diff the previous and current domain and
deliver changed and removed keys to the local observer snapshot during
`poll_external`/`wait_external`. The cross-process smoke verifies FIFO order,
reloaded values, and callback delivery; native Darwin notification-center
semantics remain outside this adapter.

Preference loading now compares the main plist and orphaned `.tmp` by write
time and selects the newer valid source, covering recovery after an interrupted
replacement even when an older main plist still exists.

The external `.events` queue is now serialized by a named Windows mutex for
both append and drain operations, so concurrent preference writers and readers
cannot interleave truncation or consume partial records. This closes the local
queue atomicity boundary, but not multi-file transactional journaling.

The CoreFoundation collection family now snapshots and retains array, dictionary,
and set values while applier callbacks run. Callbacks may remove or replace
entries from the mutable collection without invalidating the active iteration;
a dedicated mutation test covers all three collection types. This is still
collection-ABI coverage, not the complete CoreFoundation object model.

The same scalar family now rejects non-finite and out-of-range floating-point
to-int64 conversions without invoking undefined behavior, and gives NaN number
comparisons a deterministic unordered result.

The Release Clang build currently passes 60/60 CTest entries, including the
Mach-O printf bundle end-to-end test. The latest five local commits are ahead
of the configured remote and have not been pushed in this work cycle.

The Mach-O smoke also verifies the ARM64 execution boundary on x86_64 Windows:
ARM64 headers, relocation records, and chained fixups are parsed and patched,
but `ExecuteEntryNoArgs` rejects ARM64 with a deterministic fail-closed error.
This is an execution-boundary test, not ARM64 runtime support; native ARM64
execution still requires an ARM64 Windows backend and a valid executable
fixture.
