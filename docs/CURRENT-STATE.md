## Execution boundary

The supported architecture target is the native Windows adapter and runner;
WSL is optional reference/backend infrastructure, not a runtime prerequisite.
On the current host, direct WSL probing returns `Wsl/E_ACCESSDENIED`, so no
WSL-backed Darling execution is claimed or required for the native smoke-test
suite.

The native `wintosh.exe` Release target was built and verified with
`--help`, `--version` (`Wintosh 0.1.1`), and `--diagnose-host`. The host
diagnostic confirms the current x86_64 native target and the fail-closed
boundaries for i386/ARM64 on this host. A repository-owned synthetic x86_64
Mach-O fixture is now bundled, so `--inspect` and native execution are proven
for that controlled fixture; arbitrary macOS binaries remain unclaimed.

The runner also provides `--init-prefix <directory>`, which creates the
minimal Darwin directory layout without downloading or fabricating Apple
libraries.  The repository-owned x86_64 fixture now proves `--inspect` and
native execution; real system dylibs and frameworks are still not bundled.

The runtime-provider fixture now verifies a three-image provider chain:
`RuntimeClient.macho` resolves and calls `_libSystemInit` from the repository's
own `libSystem.B.dylib`, which itself depends on the repository's own
`libsystem_platform.dylib`. This proves the native provider graph and call
path, but these files are test providers rather than Apple's system libraries.

The current native CTest inventory contains 57 tests.  The `tlv_smoke`,
`thread_smoke`, `pthread_sync_smoke`, `host_api_smoke`, and
`darwin_windows_broker_smoke` families cover the Windows-backed TLS,
pthread-lifecycle, synchronization, and Mach process boundaries.  A
repository-owned Mach-O provider containing the real section families
`__thread_data`, `__thread_bss`, `__thread_vars`, and `__thread_ptrs` now
exists at `wintosh-windows/fixtures/x86_64/tlv-provider`.  It is generated by
the `--emit-tlv` smoke utility and exercises section mapping and
initialization; it remains synthetic and is not a redistributable Apple
`libpthread` binary.

The complete current Release CTest run passes 57/57 tests.  This includes the
Mach-O/dyld, Objective-C/CoreFoundation, errno/signal, Mach IPC, process,
filesystem, socket, terminal, and Windows host-boundary families.  This is a
repository-wide regression result for the current Wintosh implementation, not
a claim of full Darling or macOS compatibility.

The runner smoke now executes a controlled `.app` bundle as well as inspecting
it: the bundle path resolves to `Contents/MacOS/<bundle-name>`, its Mach-O
entry receives the expected single argument, and the process returns exit code
1.  This is a repository-owned bundle fixture; it does not prove arbitrary
real-world application bundles or their Apple frameworks are runnable.

The bundle resolver now honors a simple XML `Info.plist` value for
`CFBundleExecutable` and falls back to the bundle directory name when the key
is absent or malformed.  The runner smoke uses a deliberately different
bundle name and executable name to verify this path.  The fixture also
includes surrounding whitespace and an attribute on the `<string>` tag,
covering these common plist formatting variants without claiming to be a
complete property-list parser.

The runner also reads the common `bplist00` binary format for the
`CFBundleExecutable` string (ASCII and basic UTF-16 strings) and retains the
directory-name fallback for unsupported or malformed plists.  The runner
smoke covers both the formatted XML path and a binary-plist bundle path; this
is intentionally a focused key reader, not a general Foundation plist API.
Binary dictionaries with an extended object count are accepted as well, while
the implementation deliberately remains bounded to the executable lookup.
Malformed binary-plist count metadata is rejected safely and uses the normal
bundle-name fallback rather than being treated as executable metadata.
The runner smoke now executes that malformed-plist fallback path end-to-end.

`MachOImage::HasCodeSignature()` and `wintosh --inspect` now expose whether an
`LC_CODE_SIGNATURE` load command is present.  This is metadata detection only:
Wintosh still does not validate the embedded Apple CodeDirectory or CMS
signature and never treats presence as authenticity.
`CodeSignatureRange()` additionally exposes the validated payload offset and
size for a future verifier, covered by the Mach-O UUID/signature smoke test.

The dyld resolver now also checks `Contents/Frameworks` and `Contents/PlugIns`
as scoped fallbacks for `@rpath/...` dependencies of a bundle executable when
the image has no explicit `LC_RPATH`.  The dyld smoke fixture proves the
`Contents/Frameworks` case; this is path resolution only and does not imply
that arbitrary Apple frameworks are executable on Windows.

Framework shorthand resolution also covers versioned bundles through
`Name.framework/Versions/Current/Name` and `Versions/A/Name`; the smoke fixture
proves the concrete `Versions/A` layout.

The Objective-C/CoreFoundation tests verify class and selector registration,
typed message-send bridges, blocks, Foundation values, run loops, and
CoreFoundation collections.  They do not provide an Objective-C exception
unwind ABI: no `@throw`/`@catch` personality routine or `objc_exception_*`
compatibility layer is currently shipped.  C++ exceptions must not be treated
as proof of that Darwin behavior.

The Wintosh-owned `objc_exception_smoke` additionally verifies a scoped
callback exception carrier: an Objective-C object can cross the bridge and be
caught by the matching Wintosh adapter, while normal callback return remains
distinct.  This is a project-local transition API, not an Apple-compatible
compiler personality or DWARF/SEH Objective-C unwind implementation.

The focused TLS/pthread regression set was rerun on the current Release build:
`wintosh_tlv_smoke`, `wintosh_thread_smoke`, `wintosh_pthread_sync_smoke`,
`wintosh_host_api_smoke`, `wintosh_dyld_smoke`, and `wintosh_macho_smoke`
all pass (6/6).  This is evidence for the Windows host bridge and loader
paths, not evidence that an arbitrary Apple pthread implementation can already
be loaded.

The adjacent startup/POSIX boundary set also passes 5/5 on Release:
`wintosh_errno_smoke`, `wintosh_signals_smoke`,
`wintosh_startup_trampoline_smoke`, `wintosh_macho_entry32_smoke`, and
`wintosh_runner_smoke`.  This verifies the current Windows-backed errno and
signal bridges, the tested startup trampoline, 32-bit entry dispatch, and
runner argument handling; it does not expand Mach-O TLS thunk support.

The executable `TLVClient.macho` currently proves the safe path: all four
Darwin TLS sections are initialized before its entry returns, and the runner
exits with code 0.  A hand-written Mach-O-side call through the initialized
`DarwinTLVDescriptor::thunk` was also isolated experimentally, but still
causes an access violation at the Mach-O-to-host ABI boundary.  That call is
therefore not shipped as a capability claim; the native `tlv_smoke` test
continues to cover the thunk and per-thread resolution directly.  The next
required step is an ABI trampoline with a verified Windows x64 call frame,
followed by a Mach-O-side value and second-thread isolation assertion.

An independent entry sentinel (`mov eax,42; ret`) returned 42 from the loaded
`TLVClient.macho`, confirming that its `LC_MAIN` address is executed.  A
RIP-relative read of the `__thread_data` template did not return the template
byte; that template is copied into per-thread storage and is not ordinary
global data at the section address.  The remaining ABI work is therefore to
reach the per-thread object through the descriptor thunk from Mach-O code.

## What is included in a source release

Include the Windows port source, all documentation, and the `licenses`
directory. Do not vendor the large upstream reference checkouts; link to the
original repositories and keep every applicable license and notice here. A
source release must not silently replace a third-party license with the
Wintosh-original MIT notice.

## What is not claimed

This manifest proves that the current files are present in this workspace. It
does not prove that all 150 Darling external components are license-cleared,
that the NTFS-incompatible Heimdal checkout is complete, that the global build
passes, or that arbitrary macOS applications run on Windows. Those boundaries
remain in [STATUS.md](STATUS.md) and [RELEASE-CHECKLIST.md](RELEASE-CHECKLIST.md).
